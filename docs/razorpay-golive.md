## Not done — our side

`describe-configuration-settings` still reports:

```
RAZORPAY_KEY_ID         = rzp_test_simulated
RAZORPAY_WEBHOOK_SECRET = absent
```

`RazorpayService` only rejects the literal placeholders `rzp_test_simulated` and
`mock`, so it is running in simulated mode and `CheckoutModal` shows "Online
payment is not enabled on this environment."

### The trap to avoid

That same check means a **real Razorpay test key** (`rzp_test_abc…`) would pass
and flip the app into live mode against Razorpay's *test* environment — checkout
would look like it works and take no real money. Always confirm the key begins
`rzp_live_`.

## To finish

Run in one shell, so the variables stay in scope:

```bash
export HISTCONTROL=ignorespace
 export RZP_KEY_ID='rzp_live_...'
 export RZP_KEY_SECRET='...'
 export RZP_WEBHOOK_SECRET='...'

# expect 23 / 24 / 64
printf 'id=%s secret=%s webhook=%s\n' \
  "${#RZP_KEY_ID}" "${#RZP_KEY_SECRET}" "${#RZP_WEBHOOK_SECRET}"

# expect 200
curl -s -o /dev/null -w "auth: %{http_code}\n" \
  -u "$RZP_KEY_ID:$RZP_KEY_SECRET" "https://api.razorpay.com/v1/payments?count=1"

aws elasticbeanstalk update-environment \
  --environment-name quadis-backend-live \
  --option-settings \
    Namespace=aws:elasticbeanstalk:application:environment,OptionName=RAZORPAY_KEY_ID,Value="$RZP_KEY_ID" \
    Namespace=aws:elasticbeanstalk:application:environment,OptionName=RAZORPAY_KEY_SECRET,Value="$RZP_KEY_SECRET" \
    Namespace=aws:elasticbeanstalk:application:environment,OptionName=RAZORPAY_WEBHOOK_SECRET,Value="$RZP_WEBHOOK_SECRET"
```

### Watch it, and do not wait politely

The last attempt wedged. **Poll every 20s from the moment you hit enter:**

```bash
watch -n20 'aws elasticbeanstalk describe-instances-health \
  --environment-name quadis-backend-live --attribute-names All \

```

If you see **"No data received from the instance"**, do not let EB run its
15-minute timeout — it will revert the config and then block every EB operation
for another 20 minutes. Reboot immediately:

```bash

```

The API answered 200 about five minutes after the reboot last time.

## The real test

A CLI check cannot prove the chain. Make one **real booking on a phone**, pay by
UPI, and watch it flip to CONFIRMED inside the 90-second poll. Then refund it
from the Razorpay dashboard.

There is no ₹1 option — the amount comes from the rate sheet, so the cheapest is
one night at Quadis Sector 51 (₹1,500 base).

If it pays but never confirms, open **Razorpay → Webhooks → delivery log**:

- **401** — the secret does not match `RAZORPAY_WEBHOOK_SECRET`
- **404** — the event carried no `bookingCode` we could resolve
- **nothing at all** — Payment Capture is on Manual, so only
  `payment.authorized` fired and we do not handle it. Set it to **Automatic**.

## Two things still wrong that this does not fix

**CloudFront masks every API error.** `/api/bookings/NOPE` returns **404 JSON**
direct from EB but **200 `text/html`** through CloudFront, because the
distribution's 403/404 → `/index.html` custom error responses cannot be scoped
per behaviour. `handlePayNow` calls `.json()` on that HTML and throws
`Unexpected token '<'`, so genuine payment errors reach the guest as a parser
error.

A CloudFront Function named **`quadis-spa-router`** is already created and
tested for this — it rewrites extensionless paths to `/index.html` on the
default behaviour only, leaving `/api/*` alone. It sits in **DEVELOPMENT stage,
attached to nothing**. To finish: publish it, attach it to the default cache
behaviour, and delete the two `CustomErrorResponses`. A full backup of the
distribution config was taken first; ETag at the time was `E23ZP02F085DFQ`.

**`trust proxy` is unset.** `awaitServerConfirmation` polls up to 36 times per
checkout (90s ÷ 2.5s) against a 100-request/15-minute limit on `/api/bookings`
that is currently shared by every visitor, because Express cannot see the real
client IP behind the load balancer. A handful of simultaneous guests can
rate-limit each other *after* paying.
